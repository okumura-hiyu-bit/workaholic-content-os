## 2.2 レイヤーごとの役割

### Web App（Next.js）
UIとAPIを同一Next.jsアプリ内に持つ。Vercelにデプロイし、リクエストごとにサーバーレス関数として実行される。管理画面としての利用が中心（同時接続数は小規模）なので、この構成で十分なスケールを確保できる。将来的にAPIの利用者が増えた場合（クライアント向けポータルが独立UIを持つ等）は `apps/` 配下にアプリを追加するだけで対応可能（後述のモノレポ構成）。

### DB / Auth / Storage（Supabase）
- Postgresを採用し、**Row Level Security（RLS）で組織（org_id）ごとにデータを分離**する。これはPhase2でクライアントが増えたときに「他社のデータが見える」事故を構造的に防ぐための最重要ポイント。
- Auth はメール＋パスワード、将来的にGoogle SSOを追加。
- Storage はサムネイル画像、台本のエクスポートファイルなどを保持する（動画本体のファイルは別途NAS/Google Drive等の既存運用を想定し、システムには「リンク」のみを持たせる。動画ファイルそのものをアップロードさせる設計にはしない＝ストレージコストと転送コストを避ける）。

### AI Layer（`packages/ai`）
Anthropic Claude APIをラップする専用パッケージ。タスクの種類ごとにプロンプトテンプレートを分離管理する：
- リサーチ系（市場リサーチ・競合分析・トレンド）→ Web検索ツールを併用
- 企画・構成系（企画立案・動画テーマ・質問リスト・台本）
- 素材系（タイトル案・サムネ案・概要欄・ハッシュタグ・切り抜き提案）
- 分析系（KPI分析・改善提案・月次レポート）

すべてのAI生成結果は `ai_generations` テーブルに保存し、**「何を入力し、何を出力したか」を必ず追跡できる**構造にする。これにより、後から「このプロンプトの精度が低い」といった改善判断ができる（プロンプトの継続的なチューニングがこのビジネスの競争力そのものになるため）。

### バックグラウンドジョブ（Inngest）
KPI取得や月次レポート生成のように「時間で起動する」「失敗時にリトライが必要」な処理はUIのリクエストと切り離し、ジョブランナーで実行する。Vercelのサーバーレス関数はタイムアウトが短いため、こうした非同期処理には向かない。

### 外部連携層
プラットフォームごとにAPIの性質が大きく異なる：
- **YouTube**: Data API / Analytics API が公式に整備されており、KPI自動取込・投稿（アップロード）まで可能。
- **Instagram**: Graph API（Business/Creatorアカウント要）でKPI取得と投稿は可能だが制約が多い。
- **TikTok**: Content Posting API はあるが審査・利用制限が厳しく、Phase1時点では「予約カレンダーに登録→人が最終ボタンを押す」運用を前提にし、自動投稿は将来対応とする。

この差異を吸収するため、`packages/integrations` に共通インターフェース（`PlatformClient`: `fetchKpi()` / `schedulePost()` / `publishPost()`）を定義し、プラットフォームごとの実装差分を隠蔽する。**自動化できない部分は無理にAPIで繋がず「人の最終確認ボタン」を残す**という思想は、そもそもユーザーが望んでいる「ディレクターは最終確認のみ担当する」という要件とも一致する。

## 2.3 マルチテナント設計（Phase2を見据えて）

- 全テーブルに `organization_id` を持たせ、RLSポリシーで強制する。
- AIプロンプトのブランドボイス設定（トーン、NGワード、ターゲット層など）も `organization_id` 単位で保持し、クライアントごとに出力トーンを変えられるようにする。
- Phase1の設計・実装がそのままPhase2の基盤になる（作り直しをしない）ことを最優先の非機能要件とする。
