# 7. 技術選定

小規模チーム（実質ディレクター1名＋今後増える編集者/アナリスト）で、**運用負荷を最小化しながら、Phase2のマルチテナント展開に耐える構成**を優先して選定する。自前でインフラを持たず、マネージドサービスを組み合わせる。

## 7.1 フロントエンド

| 技術 | 選定理由 |
|---|---|
| Next.js 15 (App Router) + TypeScript | フロント/APIを1つのコードベースで完結でき、小規模チームでも開発速度を出しやすい。Vercelとの親和性も高い。 |
| Tailwind CSS + shadcn/ui + Radix UI | Apple/Notion/Linear的なミニマルなUIを、デザインシステムをゼロから作らずに高品質に実装できる。shadcn はコード生成型で自由にカスタマイズ可能なため「黒・白・グレー＋1アクセントカラー」のブランド適用がしやすい。 |
| Framer Motion | Linear的な小気味よいトランジション（カンバンのドラッグ、タブ切替）を最小コストで実現。 |
| TanStack Query | サーバー状態管理。KPIやカンバンのようにリアルタイム性がそこまで必要ない画面に対して、キャッシュ制御がしやすい。 |
| React Hook Form + Zod | フォーム（動画詳細の各種編集）のバリデーションを型安全に統一。 |
| Recharts / Tremor | KPIダッシュボードのグラフ表示。ミニマルなデザインと親和性が高い。 |

## 7.2 バックエンド / データ

| 技術 | 選定理由 |
|---|---|
| tRPC | フロントとAPIの型を共有でき、REST定義書を別途書く手間を省ける。小規模チームでの開発速度を最優先。 |
| Prisma | スキーマ駆動でDB設計（[04-database-design.md](./04-database-design.md)）とコードの一致を保ちやすい。マイグレーション管理も容易。 |
| Supabase (Postgres + Auth + Storage) | DB・認証・ストレージ・RLSがワンストップで揃い、インフラ運用の人手をかけられない体制に最適。RLSにより組織境界の分離をDBレイヤーで強制でき、Phase2のマルチテナントセキュリティ要件を満たす。 |
| Inngest | サーバーレス環境（Vercel）のタイムアウト制約を受けずに、KPI同期・AIバッチ生成・月次レポート生成のような非同期/定期ジョブを信頼性高く実行できる。リトライ・可観測性も標準装備。 |

## 7.3 AI

| 技術 | 選定理由 |
|---|---|
| Anthropic Claude API | 長文コンテキスト（台本・企画資料の一括処理）と指示追従性の高さ、Web検索ツール連携によるリサーチ系タスクとの親和性。用途に応じてモデルを使い分ける：定型生成（タイトル案・ハッシュタグ等）は軽量モデル、リサーチ・分析・レポートのように精度が重要なタスクは高性能モデルを使う二段構成とし、コストと品質のバランスを取る。 |

## 7.4 外部プラットフォーム連携

| プラットフォーム | API | 備考 |
|---|---|---|
| YouTube | Data API v3 / Analytics API | KPI取得・投稿（アップロード）とも公式サポートが厚く、自動化の主軸にできる |
| Instagram | Graph API (Business/Creator) | KPI取得・投稿は可能。ビジネスアカウント連携が前提 |
| TikTok | Content Posting API | 審査・レート制限が厳しく、Phase1では「予約カレンダー＋人による最終実行」を基本運用とする |

## 7.5 モノレポ / DevOps

| 技術 | 選定理由 |
|---|---|
| pnpm workspaces + Turborepo | `packages/ai`・`packages/integrations`・`packages/db` を独立パッケージ化しつつ、ビルドキャッシュで開発速度を落とさない。Phase2でアプリが増えても構成を変えずに拡張できる。 |
| Vercel | Next.jsとの統合が最も深く、プレビューデプロイでディレクターがステージング確認しやすい。 |
| GitHub Actions | Lint/型チェック/テストのCI、Vercelへのデプロイトリガー。 |
| Vitest + Playwright | 単体テストとE2E（カンバンのドラッグ操作、動画詳細のタブ遷移などUI主要動線）。 |

## 7.6 意図的に採用しない選択肢

- **動画ファイル自体のアップロード・ホスティング**: ストレージ・帯域コストが大きく、システムの本質的価値（企画〜分析の仕組み化）と関係が薄いため、既存の運用（Google Drive/NAS等）へのリンクのみを保持する設計とした。将来的に必要になれば `packages/integrations` にストレージ連携を追加する形で拡張可能。
- **自前サーバー / Kubernetes**: 運用人員が確保できるまでは、マネージドサービスの組み合わせで十分。Phase2でスケールが必要になった時点で個別に再検討する。
