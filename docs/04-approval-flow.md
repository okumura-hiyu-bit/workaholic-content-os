# 4. 投稿承認フロー

## 4.1 状態遷移（8状態）

```
 素材準備中 ──ファイル投入──> AI生成待ち ──generate──> 確認待ち ⇄ 修正中
                                                        │
                                                 ★承認  ↓   ↑ 承認取消
                                                    承認済み ──┘
                                                        │
                                        ┌───────────────┴────────────┐
                                        ↓                            ↓
                                  予約投稿済み                  （ポッドキャスト）
                                        ↓                     RSSに出力され自動配信
                                     公開済み                          ↓
                                        │                          公開済み
                                     投稿失敗 ──修正して承認──> 再試行
```

**投稿処理が対象とするのは `承認済み` と `予約投稿済み` の2状態のみ**です。他の6状態は、投稿処理から見て存在しません。

## 4.2 誤投稿を防ぐ「5重の安全装置」

「承認済みでないものは絶対に公開されない」を、**運用ルールではなくコードとデータ構造で保証**します。人間の注意力や、管理画面のボタン制御には依存させません。

| # | 安全装置 | 実装 |
|---|---|---|
| **1** | **ホワイトリスト方式** | 投稿処理は `status === "承認済み"` の行**だけ**を取得。「確認待ち以外を投稿」のような否定条件は書かない。将来ステータスを追加しても、明示的に許可しない限り投稿対象にならない |
| **2** | **サーバー側での再検証** | 管理画面のボタンは「承認をリクエストする」だけ。実際に投稿してよいかの判定は必ずサーバー側（Pages Functions / GitHub Actions）で再度行う。**管理画面に不具合があっても誤投稿は起きない** |
| **3** | **必須項目の検証** | 承認済みでも、本文・メディア・投稿日時のいずれかが空なら投稿せず `投稿失敗` にする。空文字での投稿事故を防ぐ |
| **4** | **時刻ガード** | `scheduled_at` が未来の行は投稿しない。**48時間以上前の行も投稿しない**（障害復旧時に何日も前の投稿が一斉に飛ぶ事故を防ぐ） |
| **5** | **ドライラン既定** | `post` コマンドは既定でドライラン（投稿内容を表示するだけ）。実投稿には `--execute` が必要。このフラグはGitHub Actionsにのみ付与する |

さらに投稿直前に `予約投稿済み` へ書き換えてからAPIを呼ぶことで、**同じ行の二重投稿を防ぎます**（Actionsが重複起動した場合の保険）。

### ポッドキャストの場合はさらに単純です

RSSフィードは Worker が生成するたびに、**`承認済み` かつ `公開時刻到来` のエピソードだけを出力**します。承認前のエピソードは**フィードに1バイトも書き出されません**。投稿処理そのものが存在しないため、誤配信が構造的に起こり得ません（[09](./09-podcast.md) 9.4）。

## 4.3 承認作業の実際

**1収録あたり5分**を想定しています。

### Step 1. 通知
`push` 実行後、生成完了の通知が届きます（管理画面へのリンク付き）。

### Step 2. 承認キュー画面で確認
`確認待ち` のものだけが1件ずつ表示されます。1収録から生成されるのは通常7〜9件です。

```
┌─ 承認キュー（5件）───────────────────── 1 / 5 ─┐
│ ep012 ／ YouTube 本編                          │
├────────────────────────────────────────────────┤
│ タイトル                                        │
│  ● 中小企業が採用で勝つ「働く理由の可視化」        │
│  ○ 給与で大手に勝てない会社がやるべきこと          │
│  ○ 「採用は正直な自己紹介」人事部長が語る本質      │
│                                                │
│ 概要欄                    [AI再生成] [元に戻す]   │
│  ┌──────────────────────────────────────┐    │
│  │ 中小企業が採用で大手に勝つために…（編集可） │    │
│  └──────────────────────────────────────┘    │
│                                                │
│ 投稿日時  2026-07-22 18:00  [変更]              │
├────────────────────────────────────────────────┤
│  J/K 移動   E 編集   A 承認   ⌘↵ 承認して次へ    │
│         [ スキップ ]  [ 承認する ]              │
└────────────────────────────────────────────────┘
```

タイトルは候補から選ぶか、直接書き換えます。キーボードだけで流せるので、**5件が1〜2分**で終わります。

### Step 3. 承認
`承認済み` になった時点で、承認者とタイムスタンプが自動記録されます。

## 4.4 管理画面から行える操作

| 操作 | 挙動 | 制限 |
|---|---|---|
| AI生成文の修正 | インライン編集・自動保存 | 原文を保持し、いつでも復元可 |
| 投稿日時の変更 | 日時ピッカー | 過去日時は選択不可 |
| **承認** | `確認待ち` → `承認済み` | 必須項目が空ならボタンを無効化 |
| **承認取消** | `承認済み` → `確認待ち` | **公開済みには適用不可**（取り消せないため） |
| **投稿テスト** | 非公開で投稿し、実際の見え方を確認 | YouTube=`private`、TikTok=`SELF_ONLY` |
| **予約投稿** | 承認と同時に予約時刻を確定 | |
| **投稿停止** | 予約を取り消す | 投稿処理の実行中は不可 |
| **再投稿** | 失敗したものを再試行 | **`post_url` が既にある行は再投稿不可**（重複投稿の防止） |

## 4.5 投稿後

- **成功**: `posted_at` と `post_url` を自動記録
- **失敗**: `error` 列にエラー内容が入り、ダッシュボードの「投稿失敗」に表示。原因を直して `承認済み` に戻せば次のスロットで再試行
- **手動投稿の媒体**（Instagram / TikTok）: 投稿予定時刻に通知が届く。投稿後、管理画面で `post_url` を貼れば `公開済み` になり、**以降のKPI取得は自動化されます**

## 4.6 将来の緩和（Phase2）

運用が安定し、「毎回同じ箇所しか直していない」と判断できたら、段階的に自動承認を導入できます。

```
ハッシュタグのみ           → 自動承認
ショートのキャプション      → 自動承認
本編タイトル・概要欄        → 必ず人が承認（ここは自動化しない）
ポッドキャスト説明文        → 必ず人が承認
```

**ただしMVPでは全件承認制で始めます。** どこを毎回直しているかが `ai_original` との差分として蓄積され、それがプロンプト改善の入力になります（[06](./06-ai-prompts.md) 6.4）。修正作業そのものをシステムを賢くする材料に変えるほうが、結果的に早く安全に自動化に到達します。
