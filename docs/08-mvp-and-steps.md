# 8. MVP範囲と実装手順

## 8.1 位置づけの変更

> **本システムは動画編集ソフトではなく、WORKAHOLICのAIアシスタントエディターです。**

優先順位を **企画・市場調査 → 収録後の編集補助** に入れ替えました。編集者が最も時間を使う「準備・整理・反復作業」の削減を最優先にします。

**この変更により、音声ポッドキャストはPhase3に後退します。** 前回はMVPに入れていましたが、編集補助の価値のほうが圧倒的に大きいという判断です（ポッドキャストは配信の仕組みが0円で完結する一方、編集時間の短縮は毎回の収録すべてに効きます）。設計（[09](./09-podcast.md)）はそのまま残すので、Phase3で着手する際に手戻りはありません。

---

## 8.2 Phase構成

### Phase 1 — 編集補助（本MVP）

| 機能 | 内容 |
|---|---|
| 素材読込 | 命名規約に沿ったフォルダから自動認識。3人以上に対応 |
| **音声同期** | 相互相関でフレーム単位のオフセット算出 |
| **話者判定** | 別録り音声の音量比較（優先）／話者分離 |
| 文字起こし | faster-whisper・単語単位のタイムコード |
| **Premiere編集プロジェクト生成** | FCP7 XML：素材配置・同期済み・カメラ切替済み・BGM・OP/ED・ショートシーケンス |
| 字幕生成 | 字幕 / 話者名 / 強調テロップ の3本のSRT |
| マーカー生成 | `[TOPIC][LAUGH][KEY][SHORT-n][RETAKE][CHECK][SPONSOR][OP][ED]` |
| ショート候補抽出 | 6〜8本。開始/終了・タイトル・フック・選定理由 |
| 音声処理 | ★**非破壊**のノイズ軽減・ラウドネス調整（原音を上書きしない） |
| YouTube書き出し | Media Encoderプリセット＋書き出し検知 |
| 確認画面（最小） | 素材一覧・解析状況・ショート候補一覧・承認 |

### Phase 2 — 投稿と分析

YouTube投稿（本編・Shorts）／投稿文生成／KPI取得／月次レポート／管理画面の拡充

### Phase 3 — 媒体展開

Instagram Reels ／ TikTok ／ **音声ポッドキャスト** ／ 媒体別最適化 ／ 高度な分析

## 8.3 Phase1完了時に実現している状態

```
収録 → 素材をフォルダに保存 → $ contentos analyze ep012
   ↓ 15〜25分（席を離れていてOK）
Premiereを開く
   ↓ 機械的な操作 ★想定15操作・目標3分以内（実測前の目標値）
★編集の90%が完了した状態から、演出・テンポ・間の確認に入れる
   ↓
書き出し → 承認 → （Phase2で）投稿
```

**削減できる作業**: 音声同期、マルチカメラの下準備、文字起こし、字幕入力、話者名テロップ、カメラ切替の初回組み、ショート候補探し、音量・ノイズ調整、チャプター作成。

**残る作業**: 演出・ストーリー・テンポ・間・笑いの活かし方・ショートの採否。**これは編集者の仕事であり、AIが代替すべきではない領域です。**

## 8.4 実装ステップ（Phase 1）

### Step 1：土台（済 / 一部）
- [x] モノレポ、ステータス定義と遷移ルール、投稿可否判定（テスト59件）
- [ ] `analysis.json` のスキーマ定義（解析結果の単一の正）
- [ ] CLI骨組み、`init`（フォルダ・brief.md雛形の生成）

### Step 2：素材解析（4〜5日）★中核
- [ ] 素材の自動認識（`raw/` の命名規約、3人以上対応）
- [ ] **音声同期**（相互相関によるオフセット算出）
- [ ] 文字起こし（faster-whisper・単語単位）
- [ ] **話者判定**（マイク音量比較／話者分離のフォールバック）
- [ ] 笑い・盛り上がり・強調ポイントの検出
- [ ] 話題区切り・チャプター生成（AI）

### Step 3：Premiereプロジェクト生成（4〜5日）★中核
- [ ] **FCP7 XML生成**（シーケンス・トラック・同期オフセット・マーカー）
- [ ] **カメラ切替案の算出**（ルールベース・設定ファイル外出し）
- [ ] ショート候補の抽出とショートシーケンス生成（1080×1920）
- [ ] BGM・オープニング・エンディングの自動配置
- [ ] **SRT生成 3本**（字幕・話者名・強調テロップ）
- [ ] YouTubeチャプターのテキスト出力
- [ ] **Premiereでの実機検証**（★ここが最大のリスク。早めに小さい素材で試す）

### Step 4：音声処理（2日）★非破壊
- [ ] **原音の保護**（出力先が入力と同一なら実行前にエラー停止）
- [ ] ノイズ軽減（`afftdn` / `arnndn`）→ `audio/processed/*.corrected.wav`
- [ ] ラウドネス調整（`loudnorm` 2パス・-14 LUFS）
- [ ] 話者ごとのゲイン調整
- [ ] **要確認情報の検出**（クリッピング・突発ノイズ・チャンネル異常）→ `[CHECK]` マーカー
- [ ] 案件ごとの有効/無効設定（`config/audio.yml`）

### Step 5：確認画面（3〜4日）
- [ ] Cloudflare Pages + Functions、Access で認証
- [ ] 素材一覧・解析状況
- [ ] **ショート候補一覧**（選定理由・フック・尺つき、採否の決定）
- [ ] テロップ確認・投稿文確認・再生成
- [ ] 承認・承認取消

### Step 6：書き出し検知（1日）
- [ ] Media Encoderプリセットの用意
- [ ] `contentos watch`（`exports/` の監視 → 承認キューへ）

## 8.5 スケジュール（Phase 1）

```
Week 1  ████ Step 1: 土台
        ████ Step 2: 素材解析（前半：同期・文字起こし）
Week 2  ████████ Step 2: 素材解析（後半：話者判定・検出）
Week 3  ████████ Step 3: Premiereプロジェクト生成 ★実機検証を並行
Week 4  ████ Step 4: 音声処理
        ████ Step 5: 確認画面（前半）
Week 5  ████ Step 5: 確認画面（後半）
        ██   Step 6: 書き出し検知
```

**約5週間。** ただし Step 2 完了時点（2週目終わり）で「文字起こし・話者判定つきの字幕SRT」が手に入るので、**そこから部分的に実運用できます。**

### 最大のリスクと対策

**Step 3のPremiere実機検証**が唯一の技術的リスクです。FCP7 XMLの解釈はバージョンによって細部が異なる可能性があります。

**対策**: Step 3の初日に、**最小構成のXML（1クリップ＋1マーカー）をPremiereで読み込む検証**を行います。ここが通れば残りは積み上げです。通らなければ早期に方針を変えられます（EDL経由、あるいはUXPプラグインの前倒し）。**大きく作ってから試すのではなく、小さく試してから作ります。**

## 8.6 コスト方針

**固定費0円を維持します。** 今回の変更でむしろ費用リスクが下がりました。

| 項目 | 方針 | 費用 |
|---|---|---|
| **動画素材** | ★**ローカルストレージまたは外付けSSDで管理。クラウドに上げない** | 0円 |
| クラウド側が扱うもの | **メタデータと設定情報のみ**（解析結果・投稿文・承認状態・KPI） | 0円 |
| 文字起こし・話者分離・音声処理 | すべてローカル（faster-whisper / pyannote / ffmpeg） | 0円 |
| AI（話題区切り・ショート候補・文面） | Gemini無料枠 | 0円 |
| 管理画面 | Cloudflare Pages + Functions + Access | 0円 |
| データ保存 | Googleスプレッドシート | 0円 |
| **合計** | | **0円** |

**GitHub Releasesへのメディア保存は廃止しました**（前回の設計から変更）。動画をクラウドに置く必要がなくなったためです。ポッドキャストのMP3配信が必要になるPhase3で、改めて置き場を決めます。

**外付けSSDの推奨**: 4K素材のマルチカメラだと1収録で数十GB〜100GBになります。解析処理も素材の読み込み速度に影響されるため、**Thunderbolt接続のSSD**を素材置き場にすることをおすすめします（既にお使いであれば、そのパスを設定するだけです）。

## 8.7 事前に準備をお願いしたいもの

| # | 準備するもの | 所要 | 必要時期 |
|---|---|---|---|
| 1 | **ffmpeg のインストール** | 5分 | Step 2 |
| 2 | Google AI Studio APIキー（Gemini・無料） | 5分 | Step 2 |
| 3 | **検証用の収録素材1本**（引き＋寄り2台＋ピンマイク） | — | **Step 2 の初日** |
| 4 | `assets/` 一式（OP・ED・ロゴ・BGM） | — | Step 3 |
| 5 | **テロップのスタイル定義**（字幕・話者名・強調の見た目） | — | Step 3 |
| 6 | Cloudflareアカウント（カード登録不要） | 5分 | Step 5 |
| 7 | GitHubアカウント（コード用の非公開リポジトリ） | 10分 | Step 1 |

```bash
brew install ffmpeg
```

**3番が最重要です。** 実素材がないと音声同期・話者判定の精度検証ができません。**過去の収録素材で構いません**（できればピンマイクありのもの）。理想は「うまく編集できた回」と「手こずった回」の2本で、AIの提案が実際の編集判断と一致するかを比較できます。

**5番について**: テロップはSRTベースで渡し、Premiere側のキャプションスタイルで見た目を決める設計です（[12](./12-premiere-capability-matrix.md) 12.4）。既存の番組テロップの見た目を再現できるよう、フォント・サイズ・色・位置がわかる資料か、既存プロジェクトファイルをいただけると確実です。

## 8.8 確認させてください

1. **ピンマイクの運用** — 出演者ごとに別録り音声を取っていますか。話者判定の精度がここで決まるため、取っていない場合は話者分離処理（精度は落ちます）で組みます
2. **通常の出演者数** — 2人が基本で、3人以上は稀という理解で合っていますか
3. **検証用素材** — 過去の収録素材を1〜2本お借りできますか（Step 2初日に必要）
4. **Premiereのバージョン** — FCP7 XMLの検証で使うバージョンを教えてください

1〜2は設計の分岐に関わりますが、**3・4が揃わなくても Step 1・2の前半（土台・素材認識・文字起こし）は進められます**ので、先に着手します。
