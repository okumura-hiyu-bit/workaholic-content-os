# 7. 分析・レポート設計

## 7.1 KPI取得

### 実行タイミング
GitHub Actions が毎日深夜3時（JST）に `kpi:fetch` を実行し、`kpi_daily` に追記します。

### 媒体別の取得方法

| 媒体 | API | 取得内容 | 自動 |
|---|---|---|---|
| YouTube | Analytics API `reports.query` | views, impressions, **CTR**, **平均視聴維持率**, comments, shares, subscribersGained | ✅ |
| YouTube | Data API `channels.list` | 登録者数 | ✅ |
| **ポッドキャスト** | **OP3 API** | **ダウンロード数**（IAB2.0準拠）、アプリ別・地域別内訳 | ✅ |
| Spotify | — | 再生数・フォロワー・完了率 | ❌ **手動CSV** |
| Apple Podcasts | — | 再生数・完了率 | ❌ **手動CSV（規約でAPI禁止）** |
| Instagram | Graph API insights | views, reach, saved, shares | ⏸ Phase2 |
| TikTok | Display API | view/like/comment/share count | ⏸ Phase2 |
| 問い合わせ数 | — | — | ❌ 手入力 |

**手動CSVインポート**は管理画面のポッドキャスト画面にドラッグ＆ドロップするだけです（月1回・3分）。取り込んだ行は `source = manual_csv` として記録され、自動取得値と区別されます。

**取得できない指標は空欄のまま**にします。0を入れると「実際に0だった」と区別できず、平均値の計算が狂うためです。

### 公開後90日で個別取得を打ち切る
それ以降の伸びは分析上ほぼ意味がなく、API呼び出しと行数を無駄に増やすためです。累計はチャンネル単位の数値で追えます。

## 7.2 分析設計

Content Repurposing を前提にした本システムだからこそ測れる軸を、分析の中心に据えます。

### 第1段階：機械的な集計（AIを使わない）

AIに生の数値を渡すと精度が落ちるため、先にプログラムで集計します。

| 集計 | 目的 |
|---|---|
| **公開後7日時点での正規化比較** | 公開日が違う投稿を公平に比較する。これをやらないと古い投稿が常に有利になる |
| **`angle`（切り口）別の平均成績** | ★同一収録から生まれた成果物を比較するため、**編集・媒体の差を排除して「企画の差」だけを取り出せる** |
| **形式比較**（長尺 / ショート / 音声） | どの形式で届いているか |
| **媒体比較**（同一素材の媒体別成績） | どの媒体が自社に合うか |
| **タイトル型別**（疑問形 / 数値入り / 引用型） | タイトルの傾向分析 |
| 前週比・前月比、平均からの乖離が大きい投稿 | 「何かが起きた」投稿の抽出 |

**「切り口分析」がこのシステム独自の価値です。** 同じ収録から生まれたショート①とショート②の成績差は、撮影条件も話者も同じなので、**純粋に切り口の差**を示します。通常のSNS分析ツールでは測れない情報で、企画精度を上げる最短路になります。

### 第2段階：AIによる解釈（週次）

集計済みの表とメタ情報（テーマ・タイトル・サムネ文言・切り口）をAIに渡します。

```
【出力】
1. 今週の要点（3行以内）
2. 伸びた投稿とその要因の仮説（★数値の根拠を必ず添える）
3. 伸びなかった投稿とその要因の仮説
4. 次に試すべきアクション（3つ以内、実行可能な粒度で）
5. 次回の企画案（3つ、ideasシートに追記）

【制約】
- 数値の裏付けがない推測には「仮説」と明記すること
- 「もっと良いサムネにする」のような実行できない提案は禁止
- サンプル数が少ない場合（公開3本未満等）は断定せず、その旨を述べること
```

**制約を厳しくしている理由**: AIによるKPI分析は放っておくと「それらしいが中身のない文章」を量産します。数値の裏付けを強制し、サンプル不足時に断定させないことで、実際に判断材料になる出力にします。

## 7.3 月次レポート

### 出力形式

| 形式 | 用途 |
|---|---|
| **HTML** | ブラウザで確認・企業提出（そのまま印刷可） |
| **PDF** | 企業提出（HTMLから生成。MVPではブラウザの印刷機能で代替） |
| **Markdown** | 加筆修正・社内共有 |
| **CSV** | 数値の二次利用 |

### 構成


### デザイン（青・白・グレー）

```
背景          #FFFFFF
セクション背景  #F7F9FC
罫線          #E3E8EF
本文          #1F2933
補足          #6B7280
アクセント     #2563EB   （見出し・グラフ主系列）
増加          #2563EB   （青）
減少          #6B7280   （グレー）
```

- フォント: `Inter` + `Noto Sans JP`
- グラフはSVGを直接生成（外部ライブラリ不要、HTMLファイル1つで完結し、そのまま送付できる）
- 装飾は罫線と余白のみ。影・グラデーションは使わない

**減少を赤にしない理由**: 月次レポートは将来クライアントにも提出するものです。減少を赤で示すと必要以上にネガティブな印象を与え、改善提案が受け入れられにくくなります。数値は事実として淡々と示し、解釈は文章側で行います。赤は「投稿失敗」など**対応が必要な事象にだけ**使う、という原則を管理画面と共通にします（[10](./10-admin-ui.md) 10.4）。

## 7.4 確認フロー

```
月初に自動生成 → 通知 → 管理画面のレポート画面で確認・加筆
→ [確定] → HTML / PDF / Markdown / CSV を書き出し
```

AIが生成した仮説には現場感覚での補正が必要なので、確認は残します（作業は10分程度を想定）。
