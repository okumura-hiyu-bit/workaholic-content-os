# 1. 全体構成（動画SNS＋音声ポッドキャスト＋管理画面）

## 1.0 基本思想：Content Repurposing

> **1回の収録を「原資産（Source）」とし、そこから媒体ごとに最適化されたコンテンツをAIが自動生成して展開する。**

これが本システムの中核思想であり、すべての設計判断の根拠です。

```
                    ┌──────────────────────────┐
                    │   1回の収録（Episode）      │
                    │   ・本編動画（マスター）      │
                    │   ・文字起こし               │
                    │   ・ブリーフ（テーマ・要点）   │
                    └────────────┬─────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              │   AIが媒体ごとに「別のもの」として再構成    │
              └──────────────────┼──────────────────┘
                                 │
   ┌──────────┬──────────┬───────┴────┬──────────┬──────────┐
   ↓          ↓          ↓            ↓          ↓          ↓
YouTube    YouTube   Instagram     TikTok    音声       告知投稿
本編       Shorts     Reels                 ポッドキャスト
──────    ──────    ──────       ──────    ──────     ──────
検索前提   スワイプ    保存前提      離脱速い   ながら聴き   誘導
長文概要欄  短文       中規模タグ    1文       章立て必要   要約
```

**「同じ文章を各媒体にコピーする」ことは、この設計では一切しません。** 媒体ごとに読者の状態が異なるため、同じ素材から**別の作品**を生成します（[06-ai-prompts.md](./06-ai-prompts.md)）。

この思想がシステムに与える具体的な帰結は3つです。

| 帰結 | 設計への反映 |
|---|---|
| **1収録 = 親、各媒体の成果物 = 子** という階層が必須 | `episodes` → `deliverables` → `posts` の3階層データ構造（[05](./05-data-structure.md)） |
| 媒体を追加しても収録側は変わらない | `src/platforms/` にファイルを1つ足すだけで新媒体に対応（X、LinkedIn、ニュースレター等） |
| 「どの切り口が、どの媒体で効いたか」が最重要の分析軸 | 同一収録から生まれた成果物を横断比較する分析画面（[07](./07-kpi-and-report.md)） |

3つ目が特に重要です。同じ収録から生まれたショートAとショートBの成績差は、**編集や媒体の差ではなく「切り口の差」を純粋に示します。** これは通常の分析では測れない情報で、企画精度を上げる最短路になります。この比較を可能にするために、親子構造を持たせています。

## 1.2 各要素の役割と選定理由

| 要素 | 採用 | 理由 |
|---|---|---|
| 管理画面のホスティング | **Cloudflare Pages** | 無料枠が最も広い（月100GB転送）。R2・Workers・Accessと同一アカウントで完結し、管理対象が1つで済む |
| APIサーバー | **Pages Functions**（Workers） | 1日10万リクエスト無料。**SNSのアクセストークンをブラウザに出さずに済む**（これが静的サイトのみの構成を採らない理由） |
| ログイン認証 | **Cloudflare Access** | 50ユーザーまで無料。Googleアカウントでログインでき、**認証を自前実装しなくてよい**。管理画面にパスワード機能を作る必要がない |
| データ保存 | **Googleスプレッドシート** | 無料。あなたが直接開いて修正できる。管理画面が壊れても業務が止まらない |
| メディア配信 | **Cloudflare R2** | エグレス無料。ポッドキャスト配信のコストが構造的に0円になる |
| RSS配信 | **Cloudflare Workers** | 動的生成により予約公開が cron 不要で実現（[09](./09-podcast.md) 9.4） |
| 定期実行 | **GitHub Actions** | 月2,000分無料。KPI取得・SNS投稿の定時実行 |
| 生成処理 | **ローカルCLI** | 動画ファイルが手元にあるため。文字起こしもローカルで完結（費用0円） |

## 1.3 なぜ「ローカルCLI」と「ブラウザ管理画面」を併用するのか

ご要望の管理画面を作りますが、**すべてをブラウザに寄せることはしません。** 役割を明確に分けます。

| | ローカルCLI | ブラウザ管理画面 |
|---|---|---|
| 担当 | 重い処理・ファイルを扱う処理 | 確認・修正・承認・分析 |
| 具体例 | 文字起こし、音声正規化、AI生成、R2アップロード | 文面編集、日時変更、承認、KPI閲覧、レポート出力 |
| 頻度 | 収録ごとに1回 | 毎日 |
| 理由 | 数GBの動画をブラウザ経由で送るのは非効率かつ無料枠を圧迫する | どこからでも触れる必要がある |

**「日常の操作はブラウザ、素材投入だけコマンド1回」** という分担です。あなたが打つコマンドは実質 `contentos push ep012` の1回だけで、以降の作業はすべてブラウザで完結します。

## 1.4 ディレクトリ構成

```
workaholic-content-os/
├── apps/
│   └── admin/                     # ブラウザ管理画面（React + Vite）
│       ├── src/
│       │   ├── routes/            # 各画面（10-admin-ui.md 参照）
│       │   ├── components/
│       │   ├── design/tokens.css  # 青・白・グレーのデザイントークン
│       │   └── lib/api.ts
│       └── functions/             # Cloudflare Pages Functions（API）
│           ├── api/[[route]].ts
│           └── _middleware.ts     # Access のJWT検証
├── workers/
│   └── feed/                      # RSS配信Worker
│       ├── src/index.ts
│       └── src/rss.ts             # フィード生成（純粋関数・テスト対象）
├── packages/
│   ├── core/                      # ★共有ロジック（CLI・API・Workerが共用）
│   │   ├── schema.ts              # 列定義とバリデーション（Zod）
│   │   ├── sheets.ts              # スプレッドシート読み書き
│   │   ├── status.ts              # ステータス遷移ルール
│   │   └── types.ts
│   ├── ai/
│   │   ├── client.ts
│   │   └── prompts/               # 媒体別テンプレート（事業の資産）
│   ├── platforms/                 # 媒体ごとの差分を閉じ込める
│   │   ├── types.ts               # PlatformAdapter インターフェース
│   │   ├── youtube.ts
│   │   ├── instagram.ts
│   │   ├── tiktok.ts
│   │   ├── podcast.ts             # RSS経由（投稿処理を持たない特殊系）
│   │   └── manual.ts              # 書き出しのみ（Cランク媒体）
│   └── media/
│       ├── transcribe.ts          # Whisper 文字起こし
│       ├── audio.ts               # ffmpeg 抽出・-16 LUFS 正規化・ID3
│       └── r2.ts
├── cli/
│   └── src/commands/              # init / generate / stage / push / post / kpi / report
├── content/                       # 素材（.gitignore）
├── reports/                       # 生成された月次レポート
├── .github/workflows/
└── docs/
```

**`packages/core/schema.ts` を単一の正とする設計**にしています。列定義・ステータス遷移ルールをここ1か所に置き、CLI・管理画面API・RSS Workerがすべて同じ定義を参照します。これにより「管理画面では承認済みなのにCLIでは違う扱い」といった不整合が起こり得ません。承認制の安全性を担保する上での土台です。
